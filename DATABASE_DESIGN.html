DATABASE_DESIGN — 客户端本地存储

本仓无本地数据库，无 schema——业务数据（会话/笔记/记忆/工作区）全部由 chatbot FastAPI + PostgreSQL 持有，客户端仅缓存。此文档登记客户端侧的键值存储面（无表结构变更面）。

原则

  • 不做本地数据库/ORM：与源 SPA 保持同构，避免双端数据一致性成本。
  • token 跨宿主统一键名 chatllm_token；迁移 Capacitor Preferences 时保持同键镜像。
  • 未来离线缓存（4.2 能力翼）若启用，采用 Cache API/Service Worker + 现有 IndexedDB，不引入 SQL 引擎。

数据库选型决策（2026-09-23 用户质询：是否全面换 SQLite）

裁决：服务端保持 PostgreSQL（不换 SQLite）；客户端不引入本地数据库（v0）。

  • 服务端不换的依据：记忆系统 8 个服务全依赖 pgvector 向量检索（backend/app/services/memory_*.py；requirements pgvector==0.5.0）；多用户 async 并发写 + 跨表事务 + per-item savepoint（记忆整合修复波）+ JSONB 聚合（jsonb_agg 修复）均为 PG 承重语义；生产数据 129MB dump 已在 PG。SQLite 单写者模型与 sqlite-vec 成熟度均不足以承接；迁移=重写记忆检索层，收益不成比例。
  • 客户端"换 SQLite"不成立：本仓当前无本地数据库（token/皮肤在 localStorage，业务数据全在服务端）；未来离线缓存（W4/W5）若落地，SQLite/IndexedDB 是增量缓存层，与服务端 PG 并存，非替代。
  • 唯一重开条件：产品转型为单用户桌面一体机（后打包进客户端）。届时建议保留容器化 PG（已有 Docker）而非重写数据层；若必须 SQLite，向量检索需 sqlite-vec 替代评估（届时另立评估）。

同步 schema（S1 波，2026-09-24；vendored server/ 侧新增，chatbot 零改动）

云-本地协同评估（docs/AUDIT_2026-09-24_cloud_local_sync.md §3.1）落地：四张同步表，不改现有业务表语义；事件捕获走 SQLAlchemy mapper 事件（同事务 connection.execute），bulk DML 实测仅 asr.py:124（非同步域）故全覆盖。create_all 幂等建表，无迁移 SQL。

事件捕获域（S1）：conversations · messages · notes · notebooks · assistants。users 设置/memory 域（Phase 3）/运行态表（agent_tasks 等）不捕获（评估 §3.3）。Message 删除随 conversation ORM 级联逐行触发事件；payload=全行快照（字段级过滤列 S2 可调项）。user 归属：conversations/notebooks/assistants 直取 user_id；messages/notes 经父表单行 SELECT 归属。
